# Mutagen Formula host integration contract

`src/game/mutagen-formula.ts` authors all 25 imported faces in Mutagen Formula and Goblin Gimmicks. The native engine installs its setup, activation, boost, response and stage hooks. Its 41 port-level tests exercise the printed card effects; 51 additional tests in `tests/mutagen-engine.test.ts` exercise actual native dispatcher outcomes. These establish the specific paths below, not perfect behavior for every possible imported card interaction.

Primary references are the [official Green Goblin insert](https://cdn.svc.asmodee.net/production-fantasyflightgames/uploads/2026/09/mc02_green_goblin_rules_insert.pdf) and [Rules Reference 1.8](https://cdn.svc.asmodee.net/production-fantasyflightgames/uploads/2026/09/mc_rulesreference_v18_compressed.pdf). Card text remains in the pinned imported catalog; no external engine code was copied.

## Ports that require native rules

`discardTop` is a discard operation, not a draw operation. It discards exactly one top card, handles the immediate encounter reset/acceleration, and reports whether that discard emptied the deck. A numbered discard ability stops at that boundary even if a reset produced a fresh deck. A subsequent player's separate discard can use the reset deck. The host must move the real discarded instance into play even when immediate reshuffling moved it into the encounter deck. This prevents duplication.

Wicked Ambitions uses an **each time** alteration effect (RRG p. 6). It pauses the preceding discard after each Goblin minion, resolves the damage/put choice fully, then resumes discarding. The module preserves that continuation in serializable effects. The damage option is non-attack damage; putting Monster into play does not trigger its When Revealed stun.

`activate` must run the entire native attack/scheme, including defense changes, statuses, Tough, prevention, overkill, responses and stage changes. It then supplies `performed`, `damagePlaced`, and `threatPlaced` to the provided continuation. Overconfidence checks actual damage placed by the activation (including damage on an ally) or actual threat placed, rather than printed ATK/SCH or the remaining main-scheme threat after advancement. Damage tokens placed on an ally include excess beyond its remaining health before defeat (RRG pp. 14, 18); an incoming three against an ally with one remaining health still qualifies. Death from Above's stage-number modifier lasts only for that activation.

`giveBoost(..., "next")` must persist a real facedown boost card until the villain's next activation. `giveBoost(..., "current")` appends a real card to the current villain boost queue. Intimidation's Boost text names the villain literally; it does not grant a boost to an activating Villainous minion. The host must retain stored boosts during a canceled activation and consume them only on an actual activation.

`putMinion` resolves normal engagement/entry rules, including Quickstrike, without invoking When Revealed. Soldiers and Thralls put in play by boosts during villain-phase step 2 are already present when that player's minion activation point is reached (official insert p. 7). Minion activation lists therefore cannot be frozen before villain boosts resolve.

`indirect` is an explicit allocation prompt to the attacked player's identity and controlled allies. Apply per-character remaining-health limits before prevention. Aggregate the allocation into one damage packet per character, then apply normal prevention/Tough. Two points assigned to a single Tough ally consume one Tough and prevent both points. Multiple Bombs are separate packets.

Goblin Knight and Monster Boost effects shuffle the same card back only after the activation ends. Discard the boost normally after resolving its icons (RRG p. 9); the delayed effect does not retain it in a boost zone. At activation completion, remove its actual instance from its present zone before shuffling. Trigger the hidden-information guard and use the engine's seeded shuffle. Delayed effects resolve before after-attack forced responses (RRG p. 16), including when a player's elimination ends the attack early (RRG p. 34).

The forced-response scheduler must preserve the first player's explicit ordering between Retaliate, Green Goblin, Knight and Pumpkin Bombs. Revalidate each response's `sourceId` immediately before initiating it: an uninitiated in-play card ability cannot start after its source has left play (RRG pp. 23, 25). A same-title villain-stage replacement remains the same character (RRG p. 47), so a Goblin response remains eligible after Retaliate defeats the preceding stage. Preserve the response amount captured for that window.

## Current verification boundary

The 41 authored tests verify exact catalog closure, setup atomicity, multiplayer routing/order, printed/scaled values, attachment uniqueness and ties, typed payment continuations, native activation-result contracts, deck-empty stopping, put-versus-reveal behavior and all boost-star effects with test-double ports.

The 51 native dispatcher tests additionally verify real default product quantities; setup before opening hands/mulligans; standard/expert villain advancement and same-character status/attachment carry; main-scheme completion/escalation/loss; attachment actions, typed payments and cancellation; all eight boost stars in both attacks and schemes; newly entered minion activation timing; delayed boost discard/shuffle without duplicate instances; Green Goblin damage conditions; Soldier/Knight/Monster effects; each Goblin treachery; excess ally damage; indirect allocation limits and Tough packet semantics; first-player Retaliate ordering; and JSON hydration during Wicked Ambitions and retained-boost decisions. Seven adversarial dispatcher fixtures verify surviving actor/controller routing, source revalidation, same-character response snapshots, delayed return after lethal damage and elimination during an earlier boost, with every actual boost instance returned once. These fixtures pass with the installed native integration.

Unimplemented imported heroes, modular sets and campaigns remain outside this verification boundary. Scenario registration does not authorize arbitrary encounter dependencies or certify every cross-card interaction.
